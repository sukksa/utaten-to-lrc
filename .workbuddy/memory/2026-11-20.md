## UtaTen 歌词下载器（D:/github/karaoke）

从零搭了一个抓取 utaten.com 歌词的本地网页工具：Node + Express + cheerio 后端，原生 JS 前端。

**关键技术结论（从真实页面验证过的）：**
- 歌词正文容器是 `div.hiragana`；注音结构为 `span.ruby > span.rb`（汉字）+ `span.rt`（假名），行间用 `<br>`，空行是连续两个 `<br>`。
- 直接取 textContent 会把假名混进正文，必须剥掉 `.rt`（解析器里保留 `{index, base, rt}` token，前端用 `<ruby>` 渲染）。
- 搜索表单字段：`artist_name` / `title` / `body`（歌词片段），必须带隐藏字段 `sort=popular_sort_asc`、`show_artists=1`。
- 只有 `artist_name` 的 GET 查询正常；`title` 的 GET 会被源站直接重置连接（疑似 WAF/PHP 侧），因此实现了 GET → POST 表单 → 降级 `body` 的三级策略，并记录每类查询可用的方法。

**开发注意：**
- 当前沙箱的出网代理连不上 utaten.com（CONNECT 502），所以真实抓取只能靠 WebFetch/microlink 间接看页面结构；端到端用 `scripts/mock-utaten.js` + `test/fixtures` 跑通。
- 无头截图要用 puppeteer 设 viewport，`chrome --screenshot --window-size=430,932` 会渲染成更宽的视口再裁剪，看起来像横向溢出，其实是假象。

**遗留：** 需在有网环境跑 `npm run probe -- ks25070443` 确认线上结构；title 搜索的 POST 路径未能实测。

## 更正（同日，用户提供 Clash Verge 代理后实测）

用户电脑走 Clash Verge，混合端口 **7897**。通过 `ProxyAgent` + `HTTPS_PROXY=http://127.0.0.1:7897` 后可直连 utaten，于是把之前所有推断都实测了一遍：

- **更正上文的错误结论**：`title` 的 GET 查询在 Node 里完全正常（返回精确结果）。之前 WebFetch / r.jina.ai 报 `fetch failed` 是抓取工具自身的问题，不是站点封锁。因此那套 GET→POST→body 三级降级策略是多余的，已删除，搜索恢复成单次 GET。
- **搜索三态全部实测通过**：`artist_name`（YOASOBI 40 条/页）、`title`（"IRIS OUT" 精确 1 条）、`body`（歌词片段 4 条）。
- **分页是路径式 URL**：`/search/=/artist_name=…/sort=popular_sort_asc/page=2/`。页码在 path 里，不在 query 里，所以 `new URL(href).searchParams.get('page')` 永远拿不到 → 用 `href.match(/[?&/]page=(\d+)/)`。`?page=2` 查询串形式其实也能用。
- **真实歌词页验证**：`/lyric/ks25070443/` 97KB，解析出 27 行、标题/歌手/作詞作曲/发行日全对；`/lyric/rq20031716/` 66 行，注音导出 `沈(しず)むように…` 正常。
- **curl 不可信**：Windows 自带 curl 走 schannel，过代理时报 TLS handshake failed，但 Node（OpenSSL 栈）同一代理 200。诊断网络问题要用 Node 复测。
- 已加 `.env` 自动加载（`src/config.js` 里手写 15 行解析，不引依赖），`.env` 里放 `HTTPS_PROXY`，`npm start` 即生效。

**仍然成立**：`div.hiragana`、`span.ruby > .rb/.rt` 结构；无头截图要用 puppeteer 设 viewport（CLI `--window-size` 会先渲染更宽再裁剪，看着像横向溢出）。

## 歌词时间轴对齐（assets/星座になれたら）

给 `*.uta-lyrics.json` 的 lines 补 LRC 起始时间，写了可复用脚本 `scripts/apply-lrc-timing.mjs`：
`node scripts/apply-lrc-timing.mjs <lrc.txt> <lyrics.json> [--in-place]`

- 匹配方式：按 text 顺序消费 LRC 条目，比较时去掉所有空白（含全角空格）；重复句（副歌）靠顺序区分。
- 写入 `start` 作为每行第一个字段，秒（两位小数，number）；全部命中时把顶层 `timed` 置为 true。
- 该文件 37 行 / LRC 37 条非空，严格顺序一致，时间与文本逐行核对通过。原文件备份为 `.json.bak`。

## utaten_lyrics.py → Node 移植

`assets/utaten_lyrics.py` 用 Python 标准库 HTMLParser 抓 utaten 歌词页，导出 uta-annotated-lyrics JSON + 对照 TXT。
已移植为 `scripts/utaten-lyrics.mjs`（cheerio + 手动重定向校验 + setupProxy），CLI 与输出格式保持一致：
`node scripts/utaten-lyrics.mjs '<url>' [--html 本地页] [--output 不带扩展名的路径]`，也挂了 `npm run lyrics`。

- 关键结构：`.lyricBody` 下同时有 `.hiragana`（汉字+假名）和 `.romaji`（汉字+罗马音）两个区块，都是 `span.ruby > .rb + .rt`；两区块分词粒度不同（注音区「は6」为一段，罗马音区拆成「は」+「6」），所以按整行文本用 NFKC + 去空白后排队匹配，不按词下标配对。
- 标题取 `.newLyricTitle__main` 的**直接文本子节点**再去掉结尾「歌詞」，否则会把动画名副标签带进来；歌手取 `.newLyricWork__name`。
- 验证：对 `ym23010406` 重新生成，与 Python 版产物除换行符外逐字节一致（Python 在 Windows 写 CRLF，Node 写 LF）；`--html` 离线解析结果与联网一致。
- 脚本拒绝覆盖已存在文件（和 Python 版一致）。

## apply-lrc-timing 匹配规则调整

比较歌词文本时改为「NFKC 归一化 + 去掉所有非文字/非数字字符」（`/[^\p{L}\p{N}]+/gu`），空白、标点、括号、emoji、♪ 都不参与比较；纯符号行（如 `♪♪`）归一化后为空串，回退到「只去空白」的比较，避免空串互相乱配。
回归验证：星座になれたら 仍 37/37 且结果与之前逐字节一致。

## apply-lrc-timing 增加相似度兜底（第二遍）

真实 LRC（assets/123.txt ふわふわ時間）里，去符号后仍有 5 行对不上，属于字符级差异（時間/タイム、しすぎて/しぎて、ー/―、すんなり/すんあり）。
改为两遍匹配：第一遍完全一致（去空白+去符号），第二遍对剩余行做 bigram Dice 相似度，**只在前后两个已匹配时间点之间**找候选；区间内仅剩一个未用时间点时阈值放宽到 0.3（位置本身是强证据），全局兜底则要求 ≥0.75。
结果：123.txt 29/29（其中 5 行标注「≈ 相似度」输出，便于人工核对）；星座になれたら 37/37 仍逐字节不变。
